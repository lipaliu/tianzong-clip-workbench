## 当前运行方式

原片和 SRT 由浏览器直传华北2（北京）私有 TOS。北京处理器使用同地域内网读取、FFmpeg 处理和本地 PostgreSQL 持久化。外部豆包语音服务需要取件时，系统只为该音频生成短时有效的 **TOS 公网 S3 预签名 GET 地址**；常规处理仍走内网端点。火山官方端点文档区分了北京 TOS 的内网与公网 S3 地址；录音文件识别 2.0 使用 `volc.seedasr.auc` 资源并支持 MP3 输入。[1] [2]

网站前端仍使用 Cloudflare Worker。北京实例的外部 443 入站路径存在云侧 TLS 异常，因此当前两天测试期通过一条受管临时 HTTPS 隧道接入处理器；该隧道已通过 HMAC 请求验证。它适合测试，不应视为备案后的长期正式入口。

## 使用规则

1. 用户上传**视频与 SRT**时，系统优先用 SRT，不计语音识别用量。
2. 用户只上传视频时，系统自动调用录音文件识别 2.0，生成带时间戳逐字稿后继续分析。
3. 如果音频是静音、无有效语音或字幕时间码无效，系统会如实提示失败，不会伪造逐字稿或剪辑建议。
4. 3GB/8GB 原片应直接上传 TOS，不经 ECS 公网带宽；采用分片续传。此次验收验证了完整处理闭环，但**尚未使用真实 3GB 或 8GB 样本进行物理压力测试**。建议下一步各上传一条真实大文件，专门记录上传耗时、断网恢复和处理耗时。

## 成本与清理安排

当前北京 ECS 是按量测试实例，配置为 4 vCPU / 8 GiB、200 GiB 磁盘。两天测试窗口结束时，已创建名为 **“结束长岛剪辑两天测试并清理资源”** 的提醒任务；该任务会先询问是否仍有上传或分析任务，再请求确认后才释放 ECS、停止隧道、清理测试桶与测试 IAM 资源，避免误删真实用户文件或持续产生费用。

## 下一步建议

两天测试通过后，建议把处理器入口替换为已备案的自有域名和稳定隧道/负载均衡入口；如主要用户均在中国大陆，也应将前端从临时海外 Worker 迁移到国内备案后的静态托管或边缘服务。这样可去除临时隧道依赖，获得更适合长期生产的访问稳定性。
