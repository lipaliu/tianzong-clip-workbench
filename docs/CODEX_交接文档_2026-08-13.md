## 一、这份文档要解决的问题

本项目在过去数轮迭代中经历了两次重大变更：一是后端从境外环境整体迁移至火山引擎中国大陆（北京），二是上传链路从「单请求直传」改造为「分片 + 云端对账断点续传」。这两项变更都涉及大量非代码的云侧配置，而这些配置无法从版本库中读出。因此本文档的首要目标不是重述代码结构，而是把**代码之外的真实运行状态**完整交出：临时基础设施的边界在哪里、哪些配置只存在于服务器上、哪些资源会在两天测试期结束后被回收、以及接手后第一优先要做什么。

阅读顺序建议：先读第二节了解当前架构，再读第四节了解本轮修复的根因（这是最容易重复踩坑的地方），然后读第六节的清理时间点——它决定了你必须在什么时间之前完成稳定化决策。

## 二、系统架构现状

系统由三层组成，且三层分属不同的云厂商与地域，这是理解一切故障的前提。

| 层 | 载体 | 位置 | 职责 |
|---|---|---|---|
| 前端与 API 网关 | Cloudflare Worker（Next.js via vinext） | 全球边缘 | 内部登录、会话、页面渲染，并以 HMAC 签名代理请求到处理器 |
| 处理器 | Node.js + TypeScript（systemd 双服务） | 火山引擎北京 ECS | 上传凭证签发、任务队列、转写、视觉证据、候选生成 |
| 存储与模型 | 火山 TOS 私有桶 + 火山方舟 / 豆包 | 北京 | 原片与产物落地、语音转写、候选推理 |

前端会话数据存放在 Cloudflare D1，处理器任务状态存放在 ECS 本地 PostgreSQL（库名 `tianclip`，运行用户 `tianclip`）。两者不共享数据库，这一点在排查「页面看得到项目但处理器查不到任务」一类问题时很关键。

**关键的地域拓扑**：浏览器在中国大陆，Worker 在 Cloudflare 边缘，处理器与 TOS 在北京 VPC 内。TOS 同时提供内网与公网两套 S3 端点，二者**不可混用**：

> 内网端点 `tos-s3-cn-beijing.ivolces.com` 只在北京 VPC 内可解析可达；公网端点 `tos-s3-cn-beijing.volces.com` 才是浏览器与外部模型服务可达的地址。

这条区别是本轮上传失败的根因，也是后续任何涉及预签名的改动都必须复核的第一条约束。

## 三、本轮交付的能力

上传方面，超过 64 MiB 的原片自动转为分片上传，分片大小 8 MiB。断点续传不依赖浏览器本地记录，而是在恢复前先向存储服务查询真实已完成分片并与上传计划对账，因此刷新页面、断网、甚至换标签页后都能从真实断点继续；分片签名过期会自动重签。

字幕方面遵循「字幕优先」：用户上传 SRT 时直接严格解析时间码并跳过语音识别；未上传 SRT 时才调用豆包录音文件识别 2.0（资源 `volc.seedasr.auc`），音频以 MP3（16 kHz 单声道 64 kbps）提交。

分析过程以事件流增量返回，用户可以持续看到下载、私有核心校验、转写、视觉证据、候选推理等阶段进度，而不是长时间停在空白页。

界面已恢复为常规横版排版：主标题 28–38 px 且不强制折行，步骤条两栏横排，原片与字幕两张上传卡并排，说明文字 12–14 px。实现方式是在 `app/globals.css` 末尾追加四段「可读性恢复层」，而非改写既有编辑风格层——因为后者被大量选择器依赖，直接改写风险过高。细节见 `docs/ui-fix-final.md`。

## 四、本轮修复的两个根因（务必阅读）

### 4.1 浏览器上传地址曾签在内网端点上

处理器把预签名 PUT 地址签在了 TOS **内网**端点上。北京 VPC 内的一切验证（包括此前从实例内部跑的端到端验收）都能通过，但用户浏览器在公网，永远连不上该地址，表现为上传长时间卡住直至超时。

修复方式是在 `processor/src/storage.ts` 中把「交给浏览器的凭证」与「处理器自己读写」分成两个客户端：前者用公网端点签名，后者继续用内网端点，从而既保证浏览器可达，又保留同地域低延迟与零公网流量。为防止回归，新增 `processor/src/tests/browser-upload-endpoint.test.ts`，断言浏览器可见的预签名主机必须是公网端点且不得出现 `ivolces.com`。

同时，浏览器直传还需要桶级 CORS。该配置由控制台完成（实例角色是最小权限，不含桶配置写权限），规则要点如下。

| 项 | 值 |
|---|---|
| 来源 Origin | 线上工作台域名与 `http://localhost:3000` |
| 方法 | PUT / GET / POST / DELETE / HEAD |
| Allow-Headers | `*` |
| Expose-Headers | `ETag`、`x-tos-request-id` |
| Max-Age | 3600 秒 |
| Vary: Origin | 已开启 |

> `Expose-Headers` 中的 `ETag` 是硬性要求：浏览器读不到分片 ETag，分片就无法合并，续传也无法对账。

### 4.2 分片过大在弱网下会放大失败代价

实测跨境链路到北京 TOS 的上行速率约 0.2–0.3 MB/s，64 MiB 一片在约 68 秒被对端断开，而同链路 8 MiB 分片稳定成功。据此把单请求直传上限从 512 MiB 降到 64 MiB、分片大小从 64 MiB 降到 8 MiB，并把前端单片重试从 3 次提到 6 次、退避上限放宽到 8 秒、每次重试都重新签发地址。

这两个值同时存在于代码默认值与服务器环境变量中，**服务器环境变量优先**。修改时必须两处一起改，否则重新部署会出现行为不一致。

### 4.3 真实验证结果

| 阶段 | 结果 |
|---|---|
| 分片凭证签发 | 10 片，每片 8 MiB |
| 上传一半后人为中断 | 已传 5 片 |
| 云端断点对账 | 状态 `uploading`，云端确认 5 片，与实际一致 |
| 仅续传缺失分片 | 补传 5 片 |
| 合并完成 | 状态 `uploaded`，83,886,080 字节与源文件完全一致 |

处理器单元测试 113/113 通过。复现脚本为 `scripts/verify-resumable-upload.mjs`。

## 五、接手所需的运维信息

### 5.1 服务器

北京 ECS 实例 `changdao-processor-test`，规格 4 vCPU / 8 GiB，200 GB SSD，按量计费，Ubuntu 24.04，公网 IP `124.174.9.168`。部署路径 `/opt/tianclip/processor/`，两个 systemd 服务分别是 `tianclip-api`（监听 `127.0.0.1:10000`）与 `tianclip-worker`。

连接方式：

```bash
ssh -i /home/ubuntu/tianzong-clip-workbench/.secrets/deploy_key root@124.174.9.168
```

该私钥仅存在于受控环境，不在 Git 中。SSH 偶发 `Connection closed by ... port 22`，属于该实例的间歇性表现，重试即可；建议脚本中统一加 3–5 次重试。

部署一次代码改动的完整流程：

```bash
scp -i .secrets/deploy_key processor/src/<file>.ts root@124.174.9.168:/opt/tianclip/processor/src/<file>.ts
ssh -i .secrets/deploy_key root@124.174.9.168 \
  'cd /opt/tianclip/processor && npm run build && systemctl restart tianclip-api tianclip-worker'
```

### 5.2 配置文件

处理器全部运行配置在 `/etc/tianclip/processor.env`，共约 50 个键。其中与本轮改动直接相关、且**只存在于服务器上**的关键项：

| 键 | 当前值 | 说明 |
|---|---|---|
| `R2_ENDPOINT` | `https://tos-s3-cn-beijing.ivolces.com` | 内网端点，处理器自身读写 |
| `R2_PROVIDER_ENDPOINT` | `https://tos-s3-cn-beijing.volces.com` | 公网端点，浏览器直传与外部模型取件 |
| `R2_CREDENTIAL_MODE` | `ecs_role` | 走实例角色临时凭证，无长期 AK/SK |
| `R2_BUCKET` | `changdao-clip-test-20260812` | 测试私有桶 |
| `SINGLE_PUT_MAX_BYTES` | `67108864` | 超过即走分片 |
| `MULTIPART_PART_SIZE_BYTES` | `8388608` | 分片大小 |
| `MAX_UPLOAD_BYTES` | `9000000000` | 单文件上限约 9 GB |
| `DOUBAO_ASR_RESOURCE_ID` | `volc.seedasr.auc` | 录音文件识别 2.0 |

此外还有 `DOUBAO_ASR_API_KEY`、`DOUBAO_ARK_API_KEY`、`INTERNAL_API_KEYS`、`DATABASE_URL` 及 `TIANCLIP_CORE_*` 系列（私有核心版本 `1.2.3-private.1`、S3 键与 SHA-256 校验值）。这些均为敏感值，不得写入版本库或文档。

Worker 侧变量在 Cloudflare 控制台配置：`PROCESSOR_API_URL`（当前为临时隧道地址）、`PROCESSOR_KEY_ID`（固定 `sites-proxy`）、`PROCESSOR_API_SECRET`、`INTERNAL_AUTH_*`。`wrangler.jsonc` 中的 `vars` 会随构建发布，改隧道地址需要改这里并推送。

### 5.3 发布方式

前端通过 GitHub 集成自动发布：推送到 `main` 后 Cloudflare 自动构建。注意线上首页对未登录请求返回 401（含静态资源），因此不能用匿名 `curl` 判断是否发布完成，需要用已登录浏览器确认。

### 5.4 临时 HTTPS 隧道（最脆弱的一环）

北京实例公网 443 入站存在云侧 TLS 异常，无法直接对外提供 HTTPS，因此当前用 Cloudflare 快速隧道把 `127.0.0.1:10000` 暴露为一个 `*.trycloudflare.com` 地址，服务名为 `changdao-quick-tunnel.service`（另有一个历史遗留的 `tianclip-tunnel.service` 也在运行，建议接手后清理其中一个以免混淆）。

```bash
systemctl status changdao-quick-tunnel
journalctl -u changdao-quick-tunnel -n 50 --no-pager | grep -o 'https://[a-z0-9-]*\.trycloudflare\.com'
```

**这个地址在隧道重启后会变化**，一旦变化必须同步更新 Worker 的 `PROCESSOR_API_URL` 并重新发布，否则前端全部请求失败、表现与「上传不了」完全一致。这是当前架构的最大单点，也是稳定化的第一优先级。

## 七、建议的稳定化路线

**第一优先：替换临时隧道。** 备案域名 + 火山负载均衡（或修复该实例的 443 入站）是正解。只要还依赖 `trycloudflare.com`，任何一次隧道重启都会造成一次「又上传不了」。

**第二优先：把桶级配置纳入基础设施代码。** 当前 CORS 是手工在控制台配置的，重建桶会丢失，且丢失后的故障表现极不直观（上传静默失败）。建议以脚本或 Terraform 固化，并为实例角色补一条受限的桶配置写权限，或改用专用管理凭证在部署流水线中执行。

**第三优先：真实大文件压力测试。** 目前 8 GB / 3 GB 场景尚未在国内真实网络下端到端跑过（跨境沙箱链路不足以代表用户体验）。建议在国内网络下实测一次 8 GB 上传 + 完整分析，重点观察分片并发是否需要按实测带宽调优、以及长任务的租约与心跳是否稳定。

**第四优先：清理历史失败任务与重复服务。** 线上项目列表中仍有修复前遗留的失败记录（含一条「上传中断，等待断点续传」），建议提供后台清理入口或直接归档，避免用户误判当前系统状态。同时处理掉重复运行的隧道服务。

## 八、常见故障速查

| 现象 | 首先检查 |
|---|---|
| 上传一直不动、最后超时 | 预签名地址主机名是否为公网端点；桶 CORS 是否仍在 |
| 分片传完但合并失败 | `Expose-Headers` 是否仍包含 `ETag` |
| 前端所有请求失败 | 隧道地址是否变化，Worker `PROCESSOR_API_URL` 是否已同步 |
| 无 SRT 时转写失败 | `R2_PROVIDER_ENDPOINT` 是否为公网端点（外部模型需公网取件）；ASR Key 与资源 ID |
| 页面样式又变得拥挤 | 是否有新样式追加到了 `globals.css` 可读性恢复层之后 |
